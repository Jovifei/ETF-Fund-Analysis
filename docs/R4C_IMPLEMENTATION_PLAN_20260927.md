# R4C 阶段实施计划（条件版）

日期：2026-09-27。依据本项目 9 月 22 日路线图、当前源码、项目知识库及远端 ChatGPT 的 M0–M5 规划整理。实施以 R4B 最终接收为前提；此页不是应用完成或生产发布收据。

## 目标与边界

下一完整阶段交付可解释、可回放、能说明何时才确认的缠论研究结构，沿用同一 ETF 详情页和价格基准。数值由确定性代码计算；LLM 只解释冻结证据；不产生第二套正式动作，不连接券商，不把箱体或旧重叠区改名为完整缠论，不提升真实数据或预测资格。

## M0：先接受正确的实现基线

1. 读取另一个 Codex 聊天最终状态和它的验收收据；对其应用提交、测试提交、文档提交分别记录 SHA/tree。`codex/r4b-price-structure` 若仍脏或测试在运行，保持本阶段为 `PENDING`。
2. 从最终候选的 Git 对象核查与 R2–R4A 的祖先关系和完整文件清单；不要用主仓 `main` 的旧代码推断 R4B 修复缺失。
3. 在独立验收工作区复核关键合同：R2 同一读取时点、R3 模块空态、R4A 价格基准、R4B 独立触碰和生命周期、原有数据/权限/操作资格负向测试。先核对测试数据库、证据目录与进程，再运行必要命令。
4. 更新对账页、`STATUS.md`、`HANDOFF.md`、`docs/README.md` 的当前入口；生产、main、本地候选、独立验收与真实数据资格各列一项。只记录已确认事实，不抹去历史收据。

**出口**：固定候选可检查，相关测试明确绑定该树，R4B 经独立接收，下一实施分支才从该精确提交创建。任何身份或证据不明均停在 M0。

## M1：决定缠论引擎与明确口径

现有 `pyproject.toml` 声明可选 `chanlun`；`backend/app/services/kline_stabilization_service.py` 有分型/笔/线段/中枢数量摘要。先查明它实际解析到的包、源码、版本、许可证和默认规则，再与 CZSC 的当前一手源码比较。不能把现有包名当作 CZSC，也不能把摘要计数当作结构正确性。

| 工作 | 交付证据 |
| --- | --- |
| 固定候选 | 上游 Git 完整 SHA、发布工件哈希、源码路径、依赖树、许可证与 NOTICE；Python 包、Rust 组件、Skill 文本和行情数据权利分别核对。 |
| 核对能力 | 包含 K、分型、笔、线段、中枢、背驰与三类买卖点逐项说明 `supported / unsupported / research_only`，注明确认时间和最新结构重绘规则。 |
| 环境与资源 | Windows 与 Linux 独立安装/导入/固定输入回放；记录冷/热运行、CPU、内存峰值、输出规模和失败行为。未知平台或版本拒绝启用。 |
| 选择结果 | 在 `docs/audits/R4C_OSS_EVIDENCE_20260927.md` 和 `config/chan_research.json` 冻结唯一方言与配置；OSS 登记和第三方 NOTICE 同步。默认关闭新引擎。 |

选择最窄且能满足已声明能力的实现。两个包装层若共用同一核心，不能当作独立验证；不同实现的分歧须解释规则差异或定位缺陷，不能取平均值。许可证、原生工件、确认时间或目标平台任一未核实，M1 停止。

## M2：确定性结构与因果回放

先依据 M0 的 R4B 实际合同复用价格 `series_id`、`price_basis`、调整版本、输入哈希、结构状态和证据 ID。若现有模块足够，不再复制一套抽象。候选文件为 `backend/app/research/chan_contracts.py`、`chan_adapter.py`、`chan_worker.py`，以及 `scripts/validate_chan_replay.py` 与人工推导夹具；具体文件名以 M0 后的代码审查为准。

输入包括标的、周期、已结算/临时状态、按时序排序的来源 K 身份、价格口径、调整版本、输入修订/哈希和计算截止。未知量额与真实零值分开。日、周、月输入必须由同一已接受价格基准形成；未完成周期只能生成明确临时候选，不能借以后收盘确认。

每个输出结构至少记录：稳定结构 ID、修订 ID、kind/层级/方向、父结构与来源 K、几何边界、发生时间、算法确认时间、首次实际观察时间、有效区间、状态及失效原因、引擎/方言/版本、配置与输入身份。追加无关未来 K 不得任意改名历史已确认结构；历史修订生成新版本，旧证据仍可查。缺少可得时间时保持未知，不把离线重建的确认时间冒充历史当时可见。

在独立夹具中覆盖包含链、等高等低、平台、缺口、单边趋势、短历史、中枢延伸/失效、重复/冲突时间、非有限 OHLC、缺量和真实零量、拆分与未完成周期。对每个前缀比较增量结果和只用该前缀的批量结果，检查几何、身份、状态与确认时间；未来 K 的变更不能改变当时保存的结果。独立期望值不能由同一实现自动生成。背驰和买卖点若无独立定义与测试，明确标为未支持。

**出口**：必需几何与因果用例通过，跨引擎差异可解释，错误和无合法结构有不同状态。

## M3：受审计任务与不可变快照

新增的研究服务应先复用现有 `workspace/data_jobs.py` 队列和任务协议，不造第二套调度器。候选落点为 `backend/app/services/chan_structure_service.py`，并窄接 `workspace/protocol.py`、`data_jobs.py`、`worker.py`、`read_model.py` 以及既有研究包证据引用。先检查 R4B 是否已有可按修订寻址的快照；只有不足时才增加独立模型及 Alembic 迁移。

显式任务冻结既有输入并结束读事务，在 API 进程外有界计算，校验结果后短事务原子发布。同样输入/引擎/配置可复用结果；任一变化产生新修订。错误、超时和损坏输出不能覆盖上次有效快照。GET 只选择已有证据，不抓取、不排队、不写库、不运行模型或原生引擎。

状态码至少区分关闭、缺依赖、版本不支持、历史不足、价格基准无效、快照缺失/过期和 worker 失败。旧 `KlineStabilizationService` 的按需计数路径要改为同一已批准快照的读视图，或清楚标记旧结果不可验证；不能与详情页同时输出两套互相矛盾的缠论结论。

测试覆盖并发重复、同日修订、输入过期、重启/超时、超大或异常输出、部分批量失败、事务回滚、用户隔离与 GET 零副作用。新迁移在新建临时 SQLite 和隔离 PostgreSQL 上复核；缺环境时单列 `SKIPPED_ENV`，不得借用生产库。

**出口**：结果原子发布、旧证据可查、GET 只读，原始 K、单位、认证和持仓均无变化。

## M4：在现有工作站呈现结构

沿用 `frontend/src/lib/types.ts`、`chartAdapter.ts`、`components/EtfChart.vue` 和 `views/Detail.vue`，添加紧凑证据卡组件。分型、笔、线段、中枢与 R4B 箱体、旧 `chan_zone_approx` 使用不同名称和图层；中枢只绘在实际形成到有效截止区间，不铺满整个历史图，也不把形成日画成当时已确认。

候选、确认、失效、历史重建同时用文字与视觉区分。默认只显示有限个最近结构，更多历史由用户展开；图层切换保留缩放和平移。证据卡可读出方言、版本、价格基准、来源截止、形成/确认时间、父结构和缺失能力。合法的“无结构”不是系统错误。

绘制前核对标的、周期、价格口径、输入与快照身份；陈旧结构带自己的陈旧标识，不借用新报价的 fresh 状态。测试应检查实际几何端点、图层清理、延迟响应、空态/错误态、键盘和手机短屏，不能以 HTTP 200 代替视觉验收。

## M5：最终验收与收据

在最终应用提交上运行项目 venv 的聚焦/全量 pytest、Python 编译、Node 静态检查、前端 Vitest/类型/构建和隔离浏览器套件；补真实选定引擎的 Windows/Linux 回放、SQLite/PostgreSQL 迁移、资源上限、许可与密钥检查。必要测试在写入前先以失败用例或可重复复现固定缺陷。首次失败、修复复跑、环境跳过、命令输出和工件身份均保留。

资源预算先冻结再测量；远端提出的 1000 根 K 热运行 p95 不超过 2 秒、引擎进程峰值不超过 512 MiB 只作待验证初始目标，不是现有实测或已通过门禁。冷启动和多标的批次分别记录。

验收收据 `docs/audits/R4C_ACCEPTANCE_20260927.md` 必须绑定应用 SHA/tree、引擎与配置、夹具哈希、平台、原始命令输出和逐项结论。文档补交提交与应用提交分开；任何应用后改动需重验受影响门禁。代码、引擎能力、合成数据、真实数据、PIT/OOS、生产部署分别报告，不能由其中一项通过推导另一项。

## 开源采用顺序

现有 `backend/app/services/kline_stabilization_service.py` 已有可选 `chanlun` 摘要路径，但计数不能证明几何或确认时点。优先审查其真实分发包，再对照 [CZSC](https://github.com/waditu/czsc) 的当前结构 API；Skill 只供开发参考，不能绕过 Provider Adapter 抓行情。AKQuant、Qlib 等保留为后续独立回测/滚动评估参考；KLineCharts 先维持项目固定版本。任何引入须固定上游提交、分发工件、许可证/NOTICE 和依赖树，不因框架更新而静默替换现有算法。

## 后续依赖

下一动作：完成 M0 后，将此条件计划按最终 R4B 代码与收据修订为可执行版本，再开始 M1。当前不修改 R4B 在途工作树或生产。
