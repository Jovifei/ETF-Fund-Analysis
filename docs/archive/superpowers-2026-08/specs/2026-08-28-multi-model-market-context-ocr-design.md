# Multi-Model Analysis, Market Context, and Portfolio OCR Design

**Status:** Design approved in visual review on 2026-08-28; implementation not started.  
**Scope:** Private ETF/LOF research system only. No automatic trading, no broker connection, and no promotion of Mock or unverified data to actual-market evidence.

## 1. Product decision

The dashboard will use one active primary analysis model. The initial primary is a configurable Codex/OpenAI Responses API model. Claude API and DeepSeek API are registered as future providers but are disabled by default and never take over silently on a primary-provider failure.

Codex and Claude Code agent tasks are separate, asynchronous research runners. They can produce read-only candidate memos after the application has generated an evidence bundle; they do not serve page requests, query providers directly, write production databases, alter strategy settings, or place orders.

The default dashboard opens with market context: China industry/sector breadth, S&P 500, Nasdaq Composite, Nasdaq-100, a China semiconductor ETF proxy, and a Korea semiconductor ETF proxy. The two semiconductor proxy codes are selected only after their exchange symbol, Provider coverage, liquidity rule, and field-quality checks are recorded in configuration.

Portfolio screenshots are processed by local PaddleOCR by default. A cloud visual-model retry is an explicit user action, never an automatic fallback.

## 2. Non-negotiable safety boundaries

- Python remains the sole calculator for market data normalization, indicators, forecast statistics, backtests, position constraints, and signal states.
- Models receive an allowlisted research bundle and untrusted news text; they receive no tools, browser access, Shell access, database credentials, provider credentials, broker access, or write capability.
- A model output is a candidate analysis. The application validates its schema and persists it through deterministic server code with provider/model/prompt/input-hash provenance.
- No provider failure silently becomes Mock data in production. No model failure silently selects another model.
- Screenshot source files are private transient input. They are never committed, added to reports, or retained beyond the configured short-lived import session.
- Actual observations and predictions use different labels, colors, data contracts, and timestamps. A forecast must never look like an observed quote.

## 3. Provider-neutral analysis gateway

### 3.1 Contract

Each direct model adapter implements:

```text
analyze(VerifiedAnalysisInput) -> AnalysisEnvelope
```

`VerifiedAnalysisInput` contains only deterministic facts already generated by the system:

- instrument code, standard name, theme, and configured benchmark;
- source/provenance, market timestamp, freshness, degraded/Mock flags;
- precomputed indicators, signal state, portfolio exposure, and forecast statistics;
- normalized news title/body plus evidence identifiers;
- prompt version and output JSON Schema version.

`AnalysisEnvelope` stores the selected provider/model, model response status, latency, input hash, prompt version, schema version, structured output, and a sanitized failure class when applicable.

### 3.2 Direct API adapters

| Adapter | Protocol | Default state | Allowed role |
|---|---|---:|---|
| `codex_openai_responses` | OpenAI Responses API | active primary when configured | Structured news/event analysis and explanation |
| `anthropic_messages` | Anthropic Messages API | registered, disabled | Manual provider switch only |
| `deepseek_openai_compatible` | OpenAI-compatible chat/responses endpoint | registered, disabled | Manual provider switch only |

Exactly one direct adapter is primary for a run. If it is unavailable, the run is recorded as `analysis_unavailable`; it does not silently fail over. A user may later switch the configured primary provider explicitly, which creates a new model/prompt version boundary.

### 3.3 Agent-review adapters

`codex_review_runner` and `claude_code_review_runner` consume an immutable, read-only evidence bundle after close. They output a candidate research memo with citations back to bundle fields. An explicit server-side validator, not the agent, decides whether to save a memo. These runners cannot be used for intraday signals or portfolio writes.

### 3.4 Structured output

Every direct-model response must conform to this application schema:

```text
facts
inferences
risk_flags
affected_themes
impact_horizon
evidence_ids
confidence_statement
provider
model
prompt_version
```

`facts` and `inferences` remain separate. The model is forbidden from inventing price, return, indicator, probability, or trade instruction fields.

## 4. Market-context registry

Market-context instruments are configuration records rather than hard-coded business logic. Each record has:

```text
context_id, label, region, context_kind, source_symbol, display_code,
is_tradable_proxy, enabled, display_order, source_priority,
freshness_rule, verification_status
```

Required enabled records:

| Group | Display item | Role |
|---|---|---|
| China | Industry/sector breadth and rotation | Context, not a tradable single quote |
| United States | S&P 500 | Cross-market context |
| United States | Nasdaq Composite | Cross-market context |
| United States | Nasdaq-100 | Growth/technology context |
| China | Semiconductor tradable ETF proxy | Context plus trackable instrument |
| Korea | Semiconductor tradable ETF proxy | Context plus trackable instrument |

The China/Korea proxy records remain disabled until the Provider adapter returns a verified exchange symbol, daily and spot coverage, acceptable liquidity metadata, source timestamp, and no unit conflict. The UI then shows `unverified` rather than fabricating a code.

## 5. Dashboard information hierarchy

### 5.1 Observed data

Observed cards use the normal data surface. Their primary visual value is `today_pct_change`; price is secondary. Every observed card displays standard code, name, source, source/exchange timestamp, freshness/degraded state, and Mock state.

ETF identity is always written as `standard_code + name`, for example `512480.SH · 半导体 ETF`. This applies to tables, detail panels, holdings, OCR confirmation, context proxies, actual data, and forecast panels.

### 5.2 Forecast data

Forecast cards use a visually distinct forecast surface and are labeled `FORECAST · 非实际结果`. They always show horizon, p-up, expected return/range where available, sample count, calibration state, model version, and data cutoff. They never reuse the observed quote color treatment or timestamp label.

### 5.3 Portfolio input

`PORTFOLIO INPUT` becomes a dedicated entry point with:

```text
Image upload -> local OCR -> candidate row parsing -> ETF code/name resolution
-> confidence and ambiguity highlighting -> user edits -> explicit confirm -> holding upsert
```

No OCR result writes a holding automatically. The user can import multiple rows, inspect candidates, reject any row, and confirm the final edit set once.

## 6. Local OCR design

### 6.1 Default engine

PaddleOCR runs locally using a Chinese/document-capable OCR pipeline selected during environment qualification. It is the default because portfolio screenshots contain Chinese fund names, code fragments, numbers, and table-like layout.

### 6.2 Input controls

- Accept PNG, JPEG, and WebP only, with byte-size, pixel-dimension, MIME, and decode checks.
- Reject password/identity/account-number extraction fields from the candidate schema. The import only retains ETF code/name, shares, cost price, target weight, and an optional user note.
- Store source image only in a private transient import directory. Delete it after successful confirmation or cancellation; a scheduled cleanup removes abandoned sessions.
- Persist field-level confidence, normalized OCR text hash, and import status for audit. Do not persist raw screenshot pixels or full raw OCR payload as normal application records.

### 6.3 Matching and confidence

The resolver tries exact normalized `ts_code`, six-digit symbol plus known exchange, then configured instrument name. It classifies each row as `matched`, `ambiguous`, `unmatched`, or `low_confidence`.

Only `matched` rows with all required numeric fields pass automatically to the editable review grid. `ambiguous`, `unmatched`, duplicate, and low-confidence rows require an explicit user selection or correction before confirmation.

### 6.4 Cloud visual review

Cloud visual analysis is off by default. When a user explicitly selects it, the UI displays the provider/model, that the image will leave the device, and the exact purpose. The cloud result is another candidate overlay; it cannot save holdings or bypass the review grid.

## 7. Configuration model

All credentials remain only in local/server environment configuration, never in UI, Git, task reports, or prompt bundles.

```text
ANALYSIS_PRIMARY_PROVIDER=codex_openai_responses
ANALYSIS_PRIMARY_MODEL=<verified_account_model_id>
ANALYSIS_PRIMARY_MODE=responses

OPENAI_API_KEY=<server-local-secret>
ANTHROPIC_API_KEY=<server-local-secret, only when enabled>
DEEPSEEK_API_KEY=<server-local-secret, only when enabled>

OCR_MODE=local_paddle
OCR_CLOUD_REVIEW_ENABLED=false
OCR_TRANSIENT_TTL_MINUTES=15
```

Provider-specific base URLs, models, timeouts, enabled flags, and prompt versions are configured separately. Startup rejects configurations with multiple primary providers or a primary provider missing its required credentials/model ID.

## 8. Data model and audit additions

New deterministic records are required for:

- `analysis_runs`: verified bundle hash, provider, model, prompt/schema version, status, latency, result hash, and sanitized error class;
- `market_context_snapshots`: context registry item, observation, source, timestamp, freshness, and verified/Mock status;
- `holding_import_sessions`: transient session state, image hash, consent state, candidate count, expiry, and user confirmation time;
- `holding_import_candidates`: parsed fields, match state, confidence, user edits, and final holding action;
- `agent_review_candidates`: immutable bundle hash, runner identity, candidate memo hash, review status, and explicit acceptance record.

Schema changes use Alembic. OCR/image bytes are excluded from ordinary database records.

## 9. Validation requirements

### Multi-model gateway

- Contract tests use synthetic verified bundles and verify the same JSON Schema across Codex/OpenAI, Anthropic, and DeepSeek adapters.
- Tests prove exactly one primary provider is selected and failures result in `analysis_unavailable`, never silent failover.
- Tests prove no model receives a tool definition, database credential, raw provider credential, or unvalidated numeric decision field.

### Market context and UI

- Tests validate context-registry uniqueness, disabled/unverified proxy rendering, freshness/provenance labels, and today-change-first ordering.
- UI tests verify all standard ETF codes are visible and observed/forecast sections cannot share a visual status class.
- Tests verify S&P 500, Nasdaq Composite, Nasdaq-100, China semiconductor proxy, and Korea semiconductor proxy have distinct identifiers and source provenance.

### OCR

- Synthetic Chinese holding-screen fixtures cover exact matches, six-digit symbol matches, ambiguous names, low-confidence numeric fields, duplicate positions, malformed images, and expiry cleanup.
- Tests prove no import writes a holding before explicit confirmation.
- Tests prove default local mode makes no network request and cloud mode requires explicit consent.

### Regression gates

Run `pytest -q`, `python -m compileall -q backend/app`, and `node --check backend/app/static/app.js`; add targeted API/UI/OCR contract tests. Re-run the existing Mock and later real-data validation separately. No strategy version is promoted by this work alone.

## 10. Delivery sequence

1. Add provider-neutral contracts, configuration validation, schema migrations, and synthetic adapter tests.
2. Add market-context registry and snapshots, beginning with verified source records rather than hard-coded cross-market proxies.
3. Add local PaddleOCR import sessions and confirmation workflow with synthetic fixtures.
4. Add Dashboard market-context, code-first identity, today-change-first observed cards, and separate forecast visual treatment.
5. Add direct Codex/OpenAI primary adapter, then manual Claude/DeepSeek adapters and asynchronous Codex/Claude Code review runners.
6. Perform real Provider qualification before enabling cross-market context or using any result beyond local/Mock evidence.

## 11. Explicit exclusions

- Automatic order execution, broker connectivity, portfolio writes by a model or agent, model-computed indicators/forecasts, and silent provider/model fallback.
- OCR of account identifiers, passwords, identity documents, or any screenshot field outside the holding-import schema.
- Treating foreign market context, a news analysis, or a prediction as evidence that a China ETF will rise or fall.

## 12. Approval record

User-confirmed decisions:

- One primary model: Codex/API.
- Claude API and DeepSeek API supported as manually selectable future providers.
- Codex/Claude Code supported as asynchronous, read-only research runners.
- Portfolio OCR: local PaddleOCR default; cloud visual retry only after manual consent.
- ETF standard codes are always visible.
- Default context: China industry/sector, S&P 500, Nasdaq Composite, Nasdaq-100, China semiconductor tradable ETF proxy, Korea semiconductor tradable ETF proxy.
- Today percentage change is primary observed-data emphasis; price is secondary.
- Forecast background and semantic treatment are distinct from actual observations.
